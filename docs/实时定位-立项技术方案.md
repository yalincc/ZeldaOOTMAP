## 〇、一句话结论

**能做，而且不用从零逆向**：老大 11-24 指出的关键事实——项目里**已经有两套针对原生 PC 移植版的成品定位工程**（totknavi-pc / xnavi-pc，Go 写成、实机验证过）。Hookshot 与它们同属静态重编译（ARM64→原生 x86-64），内存格局同构，**整条定位管线可以直接移植**，只针对 Hookshot 实测重找偏移即可。链路走**局域网同源**（方案 A），PC 一个端口同时发地图页和坐标，手机扫二维码打开同一地址。

难点有两处：①**Hookshot 内存偏移要实测重找**（不能抄 TOTK 的死偏移，每个重编译版都不同）；②**箱庭分区映射**——OoT 是 31 张各自独立坐标系的分区图，得判"林克在哪张图"再投 uv。这两处项目都有现成底子：前者有 totknavi-pc 的三层降级框架 + BOTW 的 F10 屏幕坐标校准法，后者有 `map_projections.json`。

## 三、链路：方案 A · 局域网同源（老大已拍板）

```
PC：Hookshot（读坐标） ──> 本地定位核心 ──> HTTP 服务 :8766
                                              ├─ /pos            坐标接口
                                              └─ /oot/  静态托管 地图页副本
                                                      │ 同一 WiFi
手机：扫二维码 ──> http://PC_IP:8766/oot/?follow=1 ──> 页面与 /pos 同源 → 红点跟随
```

- **为什么必须同源**：手机若打开在线站（HTTPS），页面去请求 `http://PC_IP:8766`（HTTP）会被浏览器混合内容策略硬拦。让页面和接口都由 PC 这一个端口提供，问题消失（TOTKmap V2.4.0 已实测）。
- **二维码只是入口**：把 `http://PC_IP:8766/oot/?follow=1` 编成二维码给手机扫，扫码本身不传坐标，坐标始终走同源 HTTP 轮询。
- **防火墙头号坑**：Windows 需放行 :8766 入站，否则手机连不上（TOTKmap 真机踩过）。
- 公网中继（方案 B，手机开链接、不受 WiFi 限制）**本期不做**，留到上线阶段。

## 四、OoT 特有难点：箱庭分区映射（立项的核心工作量）

TOTK/BOTW 是一张连续大地图，坐标换算一次搞定；OoT 是 31 张分区图各自坐标，**每帧要回答两个问题**：

1. **林克现在在哪张图？**
   - 候选法：读内存里的当前 Scene/Room ID（静态重编译有符号，优先找）；
   - 兜底法：用世界坐标 + 区域边界（传送点表 + 31 张图的 `camX/camZ` 覆盖范围）反推；
   - 迷宫/室内：进入后切到该迷宫的楼层图，退出回野外（参照 TOTKnavi 的"进神庙钉入口、出神庙恢复跟随"状态机）。

2. **世界坐标落到该图的哪个像素？**
   - 直接复用 `data/map_projections.json` 的现成公式（X/Z → px/py → uv%，见《地图数据与坐标口径》§2）；
   - 复用现有 `getNodeImageRect()` 处理 `object-fit: contain` 的渲染矩形对齐。

> 这一层是"实时定位"从 TOTK 平移到 OoT **真正要写的新代码**，其余（读内存、HTTP、二维码、红点跟随）都是搬现成。

## 八、阶段 0 实测结果（2026-11-24 当天完成）

> 探针：`tools/ootnavi/probe.py`（ctypes+numpy，只读）/`hunt.py`（两轮差分）。已实测附加运行中的 Hookshot。

### 8.1 已确认的参数

| 项 | 结果 | 依据 |
|---|---|---|
| 进程 | `hookshot.exe` 两个 PID（启动器 200KB / 本体 572MB），选内存大的 | `OpenProcess` 实测 |
| guest heap 宿主映射 | **`0x100000000000`**（AllocationBase），约 4.3~5.3 GB | `VirtualQueryEx` 实扫；日志 `heap: 6894 MB at 0x1000000000` 对应 |
| guest image | 日志 `image 96 MB at 0x80000000`（guest VA），宿主映射另有偏移 | 日志实读；MOD0 找到一处 `0x10008000301C` |
| 传送点锚点表 | TPP2 格式，定长 **0x80**/条，**190 个**；坐标在记录 base 的 `+0x38/+0x3C/+0x40` = (X,Y,Z) | `teleport_places.bin` 实读，`KokiriForest_Child#0`=(87.47,115.60,-26.75) ✓ |
| **林克坐标结构** | **步长 0x10 的运动环缓冲（RingBuffer）**：每 0x10 = `(X, Y, Z, -0.4)` 四个 float，marker 恒 `-0.4`；示例头 `0x10106777F380`，约 11 组有效槽 | 差分找到活槽后 dump 周围内存确认 |

### 8.2 关键发现：单地址读会"乒乓跳变"

- 差分法（走动前后对比）找到活槽 `0x10106777F3A0`，但 `watch` 显示它在几个**固定的历史坐标值间来回跳**（48.5 / 21.2 / 8.9 / 67.7…），位移 20~50m。
- 根因：锁中的是**环形缓冲的当前写入槽**，写入索引每帧轮转 → 同一地址轮流被写成不同历史帧坐标。
- 这不是 bug，是 xnavi 手册 §三记载的同一类问题（totknavi-pc 的"乒乓振荡自愈"、TOTK 的"28B RingBuffer"）。**totknavi-pc/tracker.go 已有成熟解法**。

### 8.3 下一步（阶段 1 方向调整）

1. **按 RingBuffer 读整组取最新**：连续读 11 组 `(X,Y,Z,-0.4)`，过滤垃圾值（如 `1.17e24` 未初始化槽），取"最近写入"的一组作为当前坐标（相邻帧误差 <10m，箱庭地图够用）。
2. **找基址固定偏移**：`0x10106777F380` 是本次会话地址；需像 totknavi-pc 那样找"主模块固定基址 + 静态指针链"，让重开游戏也能秒锁（当前地址重启会变）。
3. 轴序确认：RingBuffer 的 `(X, Y, Z)` 中 Y≈99~119 是高度，X/Z 是水平——与传送点表 `(87.47, 115.60, -26.75)` 的 Y=高度一致，**轴序 = (X东, Y高, Z北)**，无需 TOTK 那种 -105 偏置。
4. 移植 totknavi-pc 的 tracker（乒乓自愈 + 死守）与 server_pc.go（/pos + 同源托管 + 二维码）。

### 8.5 存档锚点尝试（老大 13:04 指导：用存档坐标确认 addr）

  - `caption.sav` 返回坐标在 **0x2A0**，`progress.sav` 在 **0x1B4B0/1B4D4/1B528**（同坐标 3 副本）

- **结构指纹扫描成功**（`structscan.py`）：用 marker=-0.4 + 步长0x10 + 连续≥5组，扫出 **105 条轨迹缓冲**，全在 `0x101067xxxxxx`；坐标全是科奇里森林范围（X -10~65 / Y 99~119 / Z -19~24）。

### 8.7 存档真值验证完成（13:17 老大原地存档后）

**存档坐标**（slot_01 原地存档）：caption 0x2A0 / progress 0x1B4B0 = **(-12.058, 103.665, 10.319)**（ZoraDomain 场景内恢复点）。

**验证结果（决定性）**：
- 结构指纹扫出 105 条 `(X,Y,Z,-0.4)` 步长0x10 的缓冲，全在 `0x101067xxxxxx`。
- 按存档真值排序，**4 个副本的 [0] 帧** `(-10.047, 103.961, 10.875)` 距存档点均 **2.11m**（最近），地址：`0x1010676FAE90` / `0x1010676FE190` / `0x10106784ACF0` / `0x10106784D990` → 这就是林克真身轨迹（2m 偏差 = 恢复点 vs 当前站位）。
- dump 完整缓冲（32 组）发现**不是环形缓冲，是定长历史轨迹数组**：`[0..21]` 一组时代轨迹（童年，靠近存档点），`[22..31]` 另一组（成年，Y=113），`[32+]` marker=0 结束。**[0] 帧 = 当前时代最新位置**。
- 多副本 + 各副本更新时刻不同 → 单地址 watch 会在几个历史值间跳（monitor.py 40s 采样证实：所有候选首帧都在 6~7 个固定值间轮转，总位移上千m 是假象）。

**★ 最终读法（阶段 1 实现依据）**：
1. 用 marker=-0.4 结构指纹定位**主轨迹缓冲**（哪条是主副本待阶段 1 用"连续跟随"确认；候选为上述 4 个镜像之一）。
2. 读缓冲 `[0]` 帧作为当前坐标（X东, Y高, Z北，无偏置）。
3. 交叉验证：多副本 [0] 帧取**众数**（4 个副本值一致时采信），单副本跳变时拒收 → 解决乒乓问题。
4. 时代切换：[0..21] / [22..31] 两段分别对应童年/成年，按当前时代取对应段的 [0]。
5. 基址固定：当前 `0x101067xxxxxx` 本次会话有效，重开需重扫（阶段 1 后期做静态指针链固定）。

**结论**：定位结构(addr + 读法)已完全确认，阶段 0 达成目标。老大要求的"存档坐标确认 addr"方法成功。
