## 1. 为什么做这个

现在的拓扑导图把 31 张区域地图缩成 400~560 px 的小卡片：能看清「哪连哪」，但**看不清单个区域里还漏了哪个点**。
TOTKmap 的形态是「一张图铺满屏 + 密集点位 + 左栏筛选 + 点开详情」，OoT 官方又是箱庭分区地图，所以正确解法不是全球瓦片，而是：

- **区域单图模式（默认）**：当前区域一张官方地图铺满画布，点位按真实坐标密集落图，滚轮/双指缩放，查漏补缺。
- **拓扑导图模式（保留）**：现有 31 节点 + 33 连线，解决「从 A 怎么走到 B、哪条是近道」。

两个模式共用同一套 `pins_data.js`（362 点）、同一份筛选/进度/详情卡逻辑。

## 2. 信息架构（先定「什么在哪、点一下发生什么」）

```
顶栏：汉堡(手机) · 品牌 · [模式切换：区域地图 | 拓扑导图] · [全部|童年|成年] · 进度条 · 全收集攻略 · 校准 · 隐藏已收集 · 中/EN
左侧栏（两种模式共用）：
  ├ 搜索框（输区域/点位/物品，回车或点结果直达）
  ├ 区域列表（区域模式默认展开 = 30 个可进入区域，带点位数量）
  ├ 分类筛选（12 类 + 全选/清空 + 计数）
  └ 快速跳转芯片（区域模式：海拉鲁地标；拓扑模式：出入口节点）
主画布：
  ├ 区域模式：一张区域图 + 密集 pin + [floor 条：All|1F|2F|...]（仅迷宫）+ 缩放控件
  └ 拓扑模式：现有节点卡片 + 连线 + 出入口提示卡
右下/底部：详情卡（点 pin 打开；手机上变为底部面板）
左下：版本徽章
```

**点一下发生什么**

| 操作 | 区域模式 | 拓扑模式 |
|---|---|---|
| 点区域列表项 | 切到该区域，`fit` 全图，pin 重渲染 | 相机聚焦该节点 |
| 点 pin | 打开详情卡（含「在本区高亮」） | 同左（现有行为） |
| 点楼层条 | 只换底图 + 过滤该层 pin，相机保持 | — |
| 点连线 | — | 显示近道说明卡，可双向跳转（现有） |
| 点搜索结果 | 若跨区域：先切区域/楼层，再打开详情卡 | 聚焦节点后打开详情卡 |
| 双指/滚轮 | 以指针为中心缩放，pin 恒定屏幕尺寸 | 现有相机 |
| 拖动空白 | 平移（有边界约束，不拖出画布） | 现有 |

**URL 深链**：`?mode=region&area=KokiriForest&floor=1F&era=Child&pin=HP-001`；拓扑仍用 `?node=`；`?pin=` 自动推导所属模式与区域。

## 3. 数据现状与要补的索引

### 已有（全部可复用，不需重新解包）

| 数据 | 现状 |
|---|---|
| 区域 | 31 个：21 野外 + 10 迷宫（`regions.js`，含中英名、童年/成年底图、裁剪） |
| 底图 | 51 张区域 webp（10.4 MB）+ 155 张迷宫楼层 webp（16.8 MB） |
| 点位 | 362 点：218 个野外点（21 个区域，最少 HountedWasteland 1 个、GanonCastle 2 个）、144 个迷宫点（10 个迷宫） |
| 楼层图 | `topology_data.js` 的 `DUNGEON_FLOOR_MAPS` 提供 10 个迷宫「楼层 → 文件」 |
| 坐标 | 点位 `x,y` 已是裁边后底图百分比，可直接 `left/top` 渲染 |

### 需要新增（一个生成物，不手写）

`app/data/regions_view.js` —— 视图索引，由新脚本 `tools/build_view_index.py` 生成：

```
{ regions: [
    { id, zh, en, kind:"field"|"dungeon", eras:["Child","Adult"],
      maps: {Child:[file...], Adult:[file...]},
      floors: [{id:"All", file}, {id:"1F", file}, ...],
      pinCounts: { Both: n, Child: n, Adult: n } }
] }
```

生成逻辑直接读 `regions.js` + `topology_data.js` + `pins_data.js`，避免页面运行时拼装三份数据、也避免手写错。

### 已发现的两个口径问题（必须按此实现）

1. **`0F` vs `1F`**：`IceCavern` / `DodongoCavern` / `FireTemple` / `SpiritTemple` 的部分点位楼层写作 `0F`，而楼层图键是 `1F`。区域模式必须做**楼层别名** `0F → 1F`（仅在展示/过滤时映射，不改原始数据）。
2. **`GerudoTrainingGround`**：只有 `_All.webp`，没有楼层图、也没有点位。区域模式回退到 `All` 图，楼层条隐藏，显示「本迷宫暂无点位」。

## 4. 技术方案（模块化，不在一坨 app.js 上继续堆）

现状（方案期）`app.js` 1381 行，拓扑/相机/筛选/详情卡全在一处。直接把区域渲染塞进去会变成 2000 行且两套状态打架。按老大「模块化、独立目录」的要求拆成：

```
app/js/
├── core.js            # 共享：state、localStorage、筛选、进度、详情卡、搜索、时代/语言、模式路由、版本
├── view-region.js     # 新增：区域单图渲染（相机、pin 层、楼层条、边界约束）
├── view-topology.js   # 平移：现有拓扑渲染（节点卡片、连线、出入口提示），行为不变
└── app.js             # 只做启动：加载数据 → core.init() → 注册两个 view → 恢复 URL 状态
```

- **行为不变原则**：拓扑模式的所有交互在迁移前后逐项对照（31 节点、33 连线、362 pin 计数、详情卡、校准、进度），不允许借重构顺手改视觉。
- **状态单一真源**：`mode / area / floor / era / lang / cats / done / hideDone / zoom / pan` 只在 `core.js` 里存一份；两个 view 只读状态、只画。
- **渲染分层**：`regions_view.js` 只提供索引，页面按需加载当前区域图片（其余不预加载），避免首屏 27 MB。
- **复用现有能力**：`getNodeImageRect` 的 `object-fit: contain` 对齐算法、`--zoom-inv` 反向缩放、详情卡、校准坐标存储原样搬过去。
- **不新增依赖**：仍然纯静态零构建。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 拆分 core/view 造成拓扑回归 | 先做「行为不变」迁移，逐项截图对照；P3 前不改拓扑视觉 |
| `0F/1F` 别名漏配 | 索引生成时建立 `floorAlias` 表并在验收里断言每层都有图 |
| 区域图过大（单张 2~5 MB） | 只加载当前区；切区时保留上一张做淡入，避免白屏 |
| 校准模式与区域模式坐标叠加 | 校准仍存 `{pinId: {x,y}}`，渲染时优先自定义坐标，逻辑与拓扑一致 |
| localStorage 老 key | 沿用 `oot_map_done_pins_v3` / `oot_map_custom_coords_v2`，不换 key；新增 `oot_map_mode` / `oot_map_area` |
| 点密集区（HyruleField 27 点）重叠 | pin 恒定 28~30 px + hover 提升层级；后续可加聚合（暂不做） |
| 把「单图」理解成全球瓦片 | 明确不做：OoT 是 31 张独立箱庭图 |

## 9. 原型验证结论（2026-11-24，未写入 `app/`）

用真实底图与全部 362 点做了一个工作区原型，验证形态与手感，结论：

**已证实可行**
- 官方区域图按原比例 `contain` 铺满画布，点位按百分比落图，科吉里森林 9/9、海拉鲁平原 26/26 全部对齐，没有整体偏移。
- 迷宫「全层」用 `_All.webp` 复合图，德库树 10/10 点全部落在正确房间，切到 `1F` 后自动只显示该层。
- 390 宽手机：侧栏抽屉 + 详情卡底部面板 + 双指缩放可用，图片不溢出（之前担心的右溢出确为截图裁切）。

**必须调整的三处**
1. **单层迷宫图尺寸差异极大**：德库树 1F 是窄长图，按高度适配后只占画布中间一小块。落地方案要按图类型给不同 `fit` 策略（单层图允许初始放大到画布 70% 高度并居中）。
2. **时代锁定区域会显示 0 点**：火之神殿、加侬之城在「童年」视图下点数为 0，点进去是空图。落地方案：区域列表标注「仅成年 / 仅童年」，点击时提示并一键切时代，不允许静默空白。
3. **手机顶栏进度被挤掉**：390 宽下进度条不可见。落地时手机端只保留 `已收集数/总数` 文本，进度条移入侧栏。

**待实测**：`0F → 1F` 楼层别名已在原型代码里实现，但截图组合没跑通（查询参数被转义），落地前用固定用例断言。
